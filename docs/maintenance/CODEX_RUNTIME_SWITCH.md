## 第一阶段：保存和同步代码

需用户授权提交、合入 `main`、push 和 Mac mini 部署后执行：

1. 核对本任务文件、主线与远端差异，排除忽略目录的真实调用证据和私人材料。本轮两个测试报告只存在隔离目录，不加入公开 `research/`。
2. 只提交本任务运行层、两个 runner 接线、抓取器及文档，合入实际 `main`。若发生冲突，解决后重新跑受影响检查，不覆盖其他会话改动。
3. 推送 GitHub，记录最终 SHA；核对 CI 结果。本轮没有站点数据或构建源改动，按当前 Deploy site 的 paths 不触发 Pages 内容发布；若最终 diff 改变，重新核对此结论。
4. Mac mini 现有自动拉取可能先收到提交；只在工作区干净且未运行任务时快进到批准 SHA，不使用 reset。同步 `.agents/skills/{research,stock,factcheck}` 并校验执行层能力文件哈希。保持 `com.searchx.runner` 与 `com.searchx.check-runner` disabled / 未加载。
5. 仅检查执行器、实际 SHA、状态目录和库根的存在与路径边界。保留原凭据；不读取或打印 `.env`，不直接运行 index、定时包装或同步钩子，不设置交付开关。

验收标准是批准 SHA 已到常驻机且两服务仍停止；这不等于队列或外部交付验收。

## 第二阶段：单条生产验收

另行明确授权指定任务、真实库写入、公开研究发布、Issue 状态及邮件/Bark/KV 后执行。先只读核对 approved 数量、失败缓存和待通知状态，避免一启用就跑整批。当前入口没有只处理一个指定队列 ID 的选择开关；如队列有其他任务，应先实现并离线验证明确的任务选择，不能把全队列运行当单条验收。

研究：验证宿主精准提交推送、远端确认、报告页可达、Issue done/评论及邮件。核查：验证真实 Obsidian 文件与手机 KV 全文同哈希、深链，以及获准的通知；私密核查不得进入公开仓库或站点。两者都验证同任务重试复用检查点，交付延期保留队列、不重复生成、不提前 done 或通知。

## 第三阶段：恢复周期执行

单条验收通过并有服务启停授权后，再启用相应 LaunchAgent，观察首轮及首个自然任务。loaded、退出 0 或历史已上线不能代替产物与外部效果。
